# napcat-plugin-github-sub

NapCat GitHub 订阅推送插件 - 监控仓库 Commits / Issues / Pull Requests 并渲染图片推送到群

## 功能特性

- 📦 **仓库订阅** - 订阅任意 GitHub 公开/私有仓库
- 🔔 **事件推送** - Commits、Issues、Pull Requests、评论自动推送
- 🖼️ **图片渲染** - 通过 Puppeteer 渲染推送图片，含 diff 代码高亮
- 🎨 **主题切换** - 白天/黑夜/自定义主题配色
- ✏️ **自定义模板** - 支持自定义 HTML 模板渲染推送图片
- 🔑 **多 Token 轮转** - 多个 GitHub Token 轮转使用，分摊 API 速率限制
- 👑 **权限管理** - 主人系统 + 可配置是否允许普通成员订阅
- 🎛️ **WebUI 控制台** - 可视化配置面板，管理订阅/Token/主题/模板
- ⚡ **提交实时检测** - commits 走 /commits 接口 + ETag 条件请求，304 不计配额
- 🌿 **多分支订阅** - 同一仓库可同时监控多个分支
- 🏷️ **订阅别名** - 推送标题显示自定义名称
- 🤝 **AI 更新摘要** - 可选接入大模型，为每批提交生成中文摘要

## 安装

1. 把本仓库克隆或解压到 NapCat 的插件目录（Linux 一般在 `NapCat安装目录/app_launcher/napcat/plugins/` 下）
2. 在插件目录里执行 `npm install && npm run build`
3. 构建产物是 `dist/index.mjs`，把它复制为插件根目录的 `index.mjs`（package.json 的 main 指向的是根目录）
4. 重启 NapCat，日志出现 `GitHub 订阅插件初始化完成` 即加载成功

## 指令列表

默认指令前缀为 `gh`。

| 指令 | 说明 |
|------|------|
| `gh 帮助` | 显示帮助 |
| `gh 列表` | 查看本群订阅 |
| `gh 全部` | 查看所有群的订阅（仅主人） |
| `gh 订阅 <owner/repo>` | 添加订阅（默认监控全部类型） |
| `gh 取消 <owner/repo>` | 取消订阅 |
| `gh 开启 <owner/repo>` | 开启订阅 |
| `gh 关闭 <owner/repo>` | 关闭订阅 |
| `gh 关注 <github用户名>` | 关注用户动态 |
| `gh 取关 <github用户名>` | 取消关注 |
| `gh 关注列表` | 查看本群关注的用户 |

> 监控类型、推送群、别名等细节在 WebUI 控制台管理。群聊里发的指令只影响本群；私聊里大部分写操作会被拒绝，因为私聊无法确定推送群。

## WebUI 配置面板

插件内置可视化配置面板，支持：

- 仪表盘总览（订阅数/推送群/轮询状态/GitHub 连通性测试）
- 基础配置（Token 管理/API 地址/轮询间隔/调试模式）
- 权限设置（主人 QQ/允许普通成员订阅）
- 订阅管理（添加/编辑/删除/开关订阅，群选择器，别名）
- AI 更新摘要（大模型接入与测试）
- 渲染主题（白天/黑夜/自定义配色）
- 自定义 HTML 模板（Commits/Issues/PRs/Comments，支持预览）
- 调试日志（实时查看/筛选/清除）
- 深色模式自适应

## 添加订阅

### 仓库地址的写法

WebUI 和指令都接受下面这些写法，插件会统一归一化成 `owner/repo`（全部转小写）：

```
owner/repo
https://github.com/owner/repo
https://github.com/owner/repo/tree/dev
https://github.com/owner/repo.git
git@github.com:owner/repo.git
  owner/repo          ← 前后有空格也没关系
```

带 `/tree/分支名` 的链接会顺手把分支也带上。什么都识别不出来时，WebUI 会提示「无法识别仓库名」。

归一化转小写这点是有意的：旧版本对大小写敏感，同一个仓库可能存出两套游标（`Owner/Repo` 和 `owner/repo` 各一份），升级后重复项会自动合并。

### 订阅别名

每个订阅可以起一个别名，推送和 AI 摘要的标题里会显示它。比如给 `owner/repo` 起别名《项目别名》，推送标题就是「本次更新摘要（项目别名 · owner/repo）」。不填就只显示仓库名，随时可以在编辑订阅里改。

### 多分支订阅

同一个仓库可以添加多个分支，各推各的。仓库没填分支时，插件会先问 GitHub 要默认分支；要不到（比如空仓库）就退回 `main`，并在回复里注明这是猜的。

## AI 更新摘要

可选功能，默认关闭。开启后，每轮检测到新提交时会把提交列表（含 diff 摘要）发给大模型，生成一段中文摘要推送到群里。

WebUI 里的配置项：

| 配置 | 说明 |
|------|------|
| `llm.enabled` | 总开关，默认 false |
| `llm.apiBase` | OpenAI 兼容接口地址，如 `https://api.openai.com/v1` |
| `llm.apiKey` | API Key，保存后回读显示为 `***` |
| `llm.model` | 模型名 |
| `llm.timeout` | 请求超时（毫秒），默认 15000 |
| `llm.temperature` | 采样温度，默认 0.3 |
| `llm.maxTokens` | 单次回复的 token 上限 |
| `llm.maxDiffChars` | 发给模型的 diff 字符数上限，默认 6000 |

几个实现上的取舍：

- 摘要在后台异步生成，不阻塞轮询。模型再慢也只影响摘要本身，正常推送照发
- 生成失败就静默跳过，这轮没有摘要，下轮有新提交再试
- diff 按 `maxDiffChars` 截断，控制 token 成本
- 同时最多 2 个摘要在跑，排队超了直接跳过，防止限流雪崩

## commits 数据源

这个版本把 commits 的检测接口从 `/events` 换成了 `/commits`，原因和现状都记录在这里，方便以后排查。

### 为什么换

原来所有事件都从 `/repos/{repo}/events` 一个接口拿。这个接口覆盖面广（push、issue、PR、star 都有），但拿来检测提交有两个问题：

1. 数据滞后。`/events` 是聚合接口，响应头写着可以缓存 5 分钟。实测同一仓库同一时刻，`/commits` 已经能看到 18:59 的提交，`/events` 还停在 14:00，差了近 5 小时。
2. 顺序不保证。events 按「事件进入队列的顺序」排，不是按事件发生时间。实测某个仓库最近 10 条里有 3 条时间戳比前一条旧。插件拿最新一条的 id 当游标，一旦卡在一条 star 上，后面的提交就全被当成「已处理」，仓库明明在动，群里一条消息都没有。

### 现在的做法

commits 走 `/repos/{repo}/commits`，游标用分支 head 的 sha。issues 和 pulls 仍走 `/events`，Actions 走独立的 `/actions/runs`。

轮询带上了 ETag 条件请求：

```
GET /repos/{repo}/commits?per_page=20
If-None-Match: "f235c64f997854..."

→ 内容没变时返回 304（空响应体）
→ 304 不计入 GitHub 配额
```

配额方面，以前每个订阅每分钟固定烧一次请求；现在内容没变就是 0 消耗，只有真有新东西的轮次才扣额。几个订阅挂一天，实际扣额通常只有个位数到几十次。

要退回旧行为，把 WebUI 里的「commits 数据源」切回 `events` 即可。不管哪种模式，都建议在 WebUI 里配至少一个 GitHub Token：匿名配额只有 60 次/小时，轮询场景下很快就打满。

## 常见问题

**订阅了但没推送？**

按顺序查：订阅是否开着；是否选了推送群（群为空就一条都不会发）；如果只监控了 commits，确认仓库是不是真有新提交——commits 游标对准分支 head，没有新 commit 就没有推送。

**图片怎么变成了纯文字？**

推送优先走 puppeteer 渲染，检测不到 puppeteer 插件时自动降级为文本，日志里会有 `puppeteer 渲染失败` 字样。装上 `napcat-plugin-puppeteer` 就恢复图片。

**只想要 commits 推送？**

编辑订阅，监控类型只勾 Commits。此时 `/events` 一次都不会请求。

**仓库明明存在，添加时却报 404？**

两种可能：一是 Token 无权限，私有仓库需要勾 `repo` 权限的 Token；二是仓库名写错。日志里能看到实际请求的 URL，对一下就知道是哪种。归一化失败的输入（完全不像仓库地址的）会提示「无法识别仓库名」，不会发 404 的请求。

**首次运行为什么不推送？**

插件要先记录当前进度，避免把历史提交一口气全推出去。第一轮只记游标不推送，从第二轮的新内容开始推。

**日志里的「游标已失效，重置基线」是什么意思？**

分支发生了强推（或提交太多，旧 head 掉出了最近窗口），插件不猜测该补推哪些，而是重置游标、从当前 head 继续，本轮不推送。宁可漏掉强推抹掉的那几条，也不把十几条旧提交一次性轰炸到群里。

**改了轮询间隔多久生效？**

下一个轮询周期开始按新间隔跑。

**获取分支失败？**

看 WebUI 提示的具体原因：`无法读取 xxx 的分支：<原因>` 是接口层面的问题（Token 无权限 / 网络不通 / 仓库不存在）；`没有可用分支（可能是空仓库）` 是接口正常返回但确实没有分支。`分支名不合法` / `用户名不合法` 是本地校验直接拦下的，多半是带了 `..` 或特殊字符。

**AI 摘要收不到？**

看日志：`[LLM 摘要] 请求失败: HTTP xxx` 是接口地址或 Key 的问题；`[LLM 摘要] 生成失败: 请求超时` 把 `llm.timeout` 调大试试；`并发已达上限，跳过` 出现在调试日志里，说明队列满了被正常跳过。

**摘要总是很啰嗦？**

提示词内置了「80-150 字、不要逐条罗列」的要求。想改口味的话，在 `src/llm.ts` 的 `DEFAULT_PROMPT` 里调整。
